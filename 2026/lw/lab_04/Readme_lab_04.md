## 1. Инженерно-педагогический сценарий

В лабораторной работе моделируется автономная система распознавания двигательной активности на периферийном устройстве:

- носимый трекер двигательной активности учащегося;
- IMU-модуль образовательного мобильного робота;
- датчик вибрации лабораторного стенда;
- локальный классификатор режима движения на STM32, ESP32 или Raspberry Pi Pico;
- модуль, работающий без постоянного соединения с облаком.

Главный инженерный вопрос:

> Как сохранить приемлемое качество классификации, если модель должна работать при ограничениях Flash/RAM и малой задержке?

В отличие от облачного сценария, TinyML-проект оценивается не только по качеству распознавания, но и по ресурсам.

## 3. Почему TinyML требует оптимизации

FP32 хранит одно число в 32 битах, то есть в 4 байтах. INT8 — в 1 байте.

Для $N$ коэффициентов оценка памяти весов:

$$ M_{FP32} = 4N $$

$$ M_{INT8} \approx N $$

Следовательно, теоретически только память весов может уменьшиться примерно в 4 раза.

**Важно:** FP32 не является принципиально невозможным на микроконтроллерах с 256–512 КБ RAM. Очень маленькая модель может работать и в FP32. Однако для практического TinyML FP32 часто проигрывает INT8 по:

- размеру прошивки;
- рабочей памяти;
- пропускной способности;
- энергопотреблению;
- наличию оптимизированных целочисленных ядер.

Кроме весов память нужна входным данным, промежуточным активациям и служебным буферам.

## 4. Многокритериальная постановка задачи

Основной критерий качества:

$$ F_1 \rightarrow \max $$

Ограничения:

$$ M \le M_{max}, \qquad T \le T_{max} $$

где:

- $F_1$ — macro-$F_1$ по выбранным активностям;
- $M$ — размер модели или потребление памяти;
- $M_{max}$ — ресурсный бюджет;
- $T$ — задержка одного вывода;
- $T_{max}$ — допустимая задержка.

Для многоклассовой задачи используется macro-$F_1$, чтобы каждый выбранный класс имел одинаковый вес в итоговой оценке.

---

## 5. Квантование INT8

Аффинная схема квантования:

$$ q = \mathrm{round}\left(\frac{r}{S} + Z\right) $$

Обратное преобразование:

$$ r \approx S(q-Z) $$

где:

- $r$ — исходное вещественное значение;
- $q$ — целое квантованное значение;
- $S$ — масштаб;
- $Z$ — нулевая точка.

Для современного LiteRT целочисленные активации обычно представляются как `int8` в диапазоне от -128 до 127.

---

## 6. Dynamic Range Quantization

Динамическое квантование выполняется после обучения:

```python
converter.optimizations = [tf.lite.Optimize.DEFAULT]
```

Характерная особенность:

- веса хранятся в пониженной разрядности;
- вход и выход обычно остаются `float32`;
- часть вычислений может выполняться с динамическим преобразованием во время вывода;
- репрезентативный набор не обязателен.

Режим удобен как простой первый уровень оптимизации.

---

## 7. Full Integer INT8

Для полной целочисленной квантизации требуется репрезентативный набор данных.

```python
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = representative_dataset
converter.target_spec.supported_ops = [
    tf.lite.OpsSet.TFLITE_BUILTINS_INT8
]
converter.inference_input_type = tf.int8
converter.inference_output_type = tf.int8
```

Репрезентативный набор должен отражать диапазоны реальных входов модели. В лабораторной работе он формируется **только из обучающей выборки**.

Full INT8 особенно важен для целочисленных микроконтроллерных и аппаратных ускорителей.

## 8. Облачный и периферийный вывод

### Облако

```text
IMU -> сеть -> сервер -> модель -> ответ
```

Преимущества:

- большие модели;
- централизованное обновление.

Недостатки:

- зависимость от сети;
- задержка передачи;
- передача телеметрии за пределы устройства.

### Edge / TinyML

```text
IMU -> локальная предобработка -> модель -> решение на устройстве
```

Преимущества:

- автономность;
- меньшая сетевая задержка;
- возможность не передавать исходный поток данных.

Ограничения:

- Flash;
- RAM;
- частота процессора;
- энергобюджет.

## 9. Предобработка IMU

Нормализация выполняется **только по обучающей выборке**.

Для каждого канала:

$$ z = \frac{x-\mu}{\sigma + \varepsilon} $$

где:

- $\mu$ — среднее по Train;
- $\sigma$ — стандартное отклонение по Train;
- $\varepsilon$ — малое число для численной устойчивости.

Параметры $\mu$ и $\sigma$ должны быть сохранены вместе с моделью: при реальном развертывании на MCU входной поток требуется преобразовывать тем же способом.

## 10. Архитектура узкого MLP

Для варианта `MLP` используется:

```text
Input 128×6
-> Flatten
-> Dense(32, ReLU)
-> Dropout
-> Dense(16, ReLU)
-> Dense(C)
```

MLP не использует временную локальность сигнала явно. Он служит компактной базовой архитектурой.

---

## 11. Архитектура 1D-CNN

Для вариантов `1D-CNN` используется:

```text
Input 128×6
-> Conv1D
-> Conv1D
-> Conv1D
-> GlobalAveragePooling1D
-> Dense
-> logits
```

Свертка вдоль времени ищет локальные паттерны ускорения и угловой скорости.

Для Варианта 25 преподавательский ноутбук использует компактную сеть:

```text
Conv1D(64, kernel=5, stride=2)
Conv1D(96, kernel=3, stride=2)
Conv1D(128, kernel=3, stride=2)
GlobalAveragePooling1D
Dense(64)
Dense(C)
```

Такая архитектура остается небольшой по сравнению с типичными облачными сетями, но содержит достаточно весов, чтобы эффект INT8-квантования был хорошо измерим.

## 12. Инженерные метрики

### 12.1. Коэффициент сжатия

Сравниваются **два FlatBuffer-файла LiteRT**:

$$ Compression = \frac{Size_{FP32}}{Size_{Edge}} $$

Это корректнее, чем сравнивать `.keras` и `.tflite`, поскольку форматы контейнеров различаются.

Размер `.keras` также фиксируется отдельно как артефакт исходной модели.

### 12.2. Потеря качества

$$ \Delta F_1 = F_{1,FP32} - F_{1,Edge} $$

Положительное значение означает ухудшение после оптимизации.

Для Варианта 25 целевой инженерный ориентир:

$$ \Delta F_1 \le 0.015 $$

То есть падение macro-$F_1$ — не более 1,5 процентного пункта.

---

## 13. Что именно измеряется в Colab

### Flash-прокси

Размер `.tflite` на диске — хороший ориентир того, сколько места потребуется для хранения модели во Flash.

### RAM-прокси

В Python-ноутбуке рассчитывается суммарный объем объявленных тензоров интерпретатора.

Это **не точный peak RAM микроконтроллера**, потому что реальная LiteRT Micro tensor arena зависит от реализации, повторного использования буферов и платформы.

### Latency

Измеряется только время:

```python
interpreter.invoke()
```

на 1000 отдельных окнах после warm-up.

Этот результат характеризует CPU среды Colab. Перед реальным внедрением задержка должна быть повторно измерена на STM32/ESP32/RP2040.
